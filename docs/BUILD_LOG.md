# 检索链路改造实录

记录本次改造做了什么、卡在哪里、怎么解决、还剩什么没做。目的是让下一次改造不用重新踩同样的坑，也让面试时能讲清楚每一个决策的来由。

时间：2026-10-04。改动前状态：词法检索 137 行、7 张事实卡、89 项测试。

## 一、目标与阶段划分

改造前项目的定位是"工程规范好、但技术难度和真实数据弱"。检索是这条链路的上限——正确的资料没被召回，后面的审校就是在错误证据上进行的。因此把检索层作为主战场，按优先级分四段：

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| P0 | 检索链路升级（BM25 + 向量 + RRF + 重排） | 已完成 |
| P1 | 真实语料生产线与 690 张事实卡 | 已完成 |
| P2 | 性能与并发（延迟优化、缓存） | 未开始 |
| P3 | 视频链路加深 | 未开始 |

执行顺序按 P0 前半（可立即验证的稀疏部分）→ P1（语料）→ P0 后半（稠密与重排，需要语料才有评测意义）。

## 二、实施步骤

1. **抽出检索抽象层**：新建 `src/growth_agent/retrieval/`，定义 `Retriever` 协议
2. **原词法实现原样迁移**为 `lexical.py`，作为不可变基线；`knowledge.py` 改为委托，签名不变
3. 跑回归测试确认行为未变（89 项通过）
4. **实现 BM25**：中文用字符 bigram（避免引入分词词典依赖），英文按词切分
5. **实现 embedding 后端抽象**：`local`（transformers）/ `api`（OpenAI 兼容，含自建 Ollama）
6. **实现向量检索**：bge 嵌入 + 磁盘向量缓存 + 暴力点积检索（数据量小时不引入 FAISS）
7. **实现 RRF 融合与 cross-encoder 重排**
8. **建立两级评测**：卡级 `retrieval-eval` + 主题级 `topic-eval`
9. **写文档采集模块** `corpus.py`：BFS 爬取 + HTML 正文提取
10. **写事实卡构建模块** `catalog_builder.py`：句子筛选 + 逐字校验 + 去重
11. **抓取真实文档并生成 690 张卡**，三重校验
12. **写 60 条自然语言查询集**，跑五策略对比
13. 更新文档、跑全量回归、提交

## 三、遇到的困难与错误

### 1. 事实卡只有 7 张时，评测完全没有区分度

**现象**：在 7 张卡的原始知识库上跑卡级评测，词法检索已经 Recall@5 = 100%、Hit@1 = 87.5%，反而比 BM25 的 81.25% 更高。所有策略都接近满分，看不出任何改进空间。

**原因**：数据规模太小，查询与卡片几乎一一对应，检索退化成"查表"。7 张卡上不存在"语义相近但词面不同"的干扰项，所以词法已经够用。

**解决**：先把语料扩到 690 张卡、84 个主题，再写不依赖知识库 slug 的自然语言查询。规模上去之后区分度立刻出现（词法 Hit@5 掉到 10.0%）。

**教训**：**评测集先于优化**。如果先写混合检索再评测，在 7 张卡上会得出"混合检索没必要"的错误结论。

### 2. 向量检索会破坏"缺证据就停止"的核心保证

**现象**：查询 `quantum chromodynamics`（与 OBS 毫无关系）时，向量检索依然返回 3 张卡，相似度 0.31–0.34。

**原因**：余弦相似度对任意两段文本都有定义，稠密检索没有天然的"无匹配"状态。而本项目最关键的设计是缺证据时返回 `insufficient_evidence` 而不是硬答——这个保证会被恒返回结果的检索器静默破坏。

**解决**：为向量检索增加相关性下限 `GROWTH_VECTOR_MIN_SCORE`，低于阈值的候选直接截断；并在评测里单独设一个指标 `absent_evidence_false_positive` 持续监控。

**教训**：引入新组件时要检查它与既有**保证**的兼容性，而不只是看它能不能跑通。这是个设计冲突，不是 bug。

### 3. 脚本文件名遮蔽标准库

**现象**：临时诊断脚本 `.cache/inspect.py` 一运行就 ImportError，报 `cannot import name ... from partially initialized module`，栈里显示 `asyncio` 导入 `inspect` 时出错。

**原因**：Python 把脚本所在目录放在 `sys.path[0]`，`inspect.py` 抢在标准库之前被导入，导致 `asyncio` 拿到的 `inspect` 是自己写的那个。

**解决**：重命名为 `probe_failures.py`。

**教训**：脚本名不要与标准库模块同名（`inspect`、`types`、`json`、`email`、`code` 都是高危名）。

### 4. 中文查询在词法检索上得分为零

**现象**：30 条中文查询在 `lexical` 和 `bm25` 上 Hit@5 全为 0.0%。

**原因**：事实卡只有英文原文，没有中文意译。词法策略在中文查询上找不到任何可匹配词元，直接返回空。

**解决**：这不是 bug，而是选型依据——引入向量检索，依靠 `bge-small-zh-v1.5` 的跨语言能力把中文分组提到 33.3%（重排后 33.3%）。

**教训**：把"必然失败的场景"单独分组报告，比只报总分更有说服力。它直接回答了"为什么需要稠密检索"。

### 5. 模型下载慢与镜像

**现象**：`huggingface.co` 完全不可达（curl 返回 000），`obsproject.com` 初次探测也失败。

**原因**：本机网络环境，HuggingFace 需走镜像。

**解决**：设 `HF_ENDPOINT=https://hf-mirror.com`；先用 curl 批量探测站点可达性，确认 `hf-mirror.com`、`obsproject.com`、`pypi.org` 均正常后再动手。`bge-reranker-base`（约 1.1 GB）下载耗时 11 分 44 秒，改用后台任务执行。

**教训**：动外网资源前先花 10 秒做可达性探测，比跑到一半失败再排查便宜得多。

### 6. reranker 输出是负数

**现象**：`bge-reranker-base` 对"更相关"的卡片输出 -6.35，对不相关的输出 -10.19，都是负数，看起来像出错。

**原因**：该模型输出的是未过 sigmoid 的 logits，不是 0–1 的概率。排序只看相对大小，负值正常。

**解决**：确认排序方向正确即可，不做归一化。文档里不把它当作可分数字使用。

### 7. Windows 上 bash + python inline 的引号地狱

**现象**：`python -c '...'` 里用 f-string 嵌套双引号，报 `SyntaxError: f-string expression part cannot include a backslash`。

**解决**：写成脚本文件再执行，不再在命令行里拼复杂代码。

### 8. git 提交被拒、推送卡住、token 前缀误删

三个连续的小坑：

- **提交被拒**：克隆下来的仓库没配 `user.name`/`user.email`，`git commit` 直接失败。解决：用历史提交里的身份做**仓库级**配置（没有动全局配置）。
- **推送卡住**：本机 git 配了 credential manager，`git push` 会停在凭据弹窗。解决：`git -c credential.helper= -c core.askPass=true push "https://user:TOKEN@github.com/..."`。
- **token 读取错误**：我用 `sed` 剥掉了 `github_pat_` 前缀，导致 `Bad credentials`。解决：直接 `tr -d '\r\n'` 读完整值，**不要**修剪前缀。

### 9. CI 要求两份样例数据逐字节一致

**现象**：CI 里有一段检查：`data/` 与 `src/growth_agent/data/` 的文件名集合必须完全相同，且每个文件必须**逐字节**相同。

**解决**：新增的两个数据文件同时写两处，并用 md5 逐个比对确认（13 个文件全部一致）。

**教训**：新增随包数据时必须同步两处，否则 CI 会挂，而本地测试不会。

### 10. 一次 flaky 测试失败

**现象**：全量测试跑出 `FAILED (errors=1)`，重跑两次均通过。发生时该次耗时从 159 秒涨到 256 秒，说明有资源竞争。

**原因**：推测与并发/超时类测试在 CPU 被其他后台任务抢占时相关；且当时用的验证环境带 `--system-site-packages`，不是纯净环境。

**状态**：**未最终定位到具体是哪个测试**。用纯净虚拟环境（与 CI 一致）连跑通过 117 项，`skipped=5`（均为需可选依赖的 FFmpeg 与 numpy 相关测试，跳过属预期）。

**教训**：跑测试时不要并行跑其他重任务。这个悬案记在这里，下次若再现应配合 `-v` 单测定位。

### 11. 文件被锁

**现象**：连续编辑同一文件时偶发 `EBUSY: resource busy or locked`。

**解决**：重试该次编辑即可。

## 四、关键设计决策（以及为什么不做别的）

| 决策 | 理由 |
| --- | --- |
| 保留词法实现作基线 | 没有固定基线就无法声称改进；新策略必须相对它测量 |
| 用 RRF 而非加权分数融合 | BM25 分数无上界、余弦有界，直接相加需要一个没有合理取值的归一化常数 |
| 中文用字符 bigram | 避免为分词引入词典依赖，且对短查询足够 |
| 不用 FAISS / Milvus | 几百条的规模上暴力点积更快、无依赖；引入近似索引是过度设计 |
| 抽取环节不用 LLM | 模型无关的抽取可复现、零成本、不会幻觉；引文必须逐字来自原文 |
| 重排只作用于融合后的 10 条候选 | 对全库重排不可接受（见代价数据） |
| 向量后端可插拔（local / api） | 本机 CPU 能跑，有 GPU 或自建 Ollama 时切 `api` 即可 |
| 补依赖走可选 extra `[embed]` | 核心安装保持 6 个依赖，不装 torch 也能跑词法与 BM25 |

## 六、P2 延迟优化（先测量，再动手）

### 12. 分阶段测量：瓶颈只有一个

| 阶段 | 耗时 |
| --- | --- |
| BM25 索引构建 | 0.24 s |
| 向量索引构建（嵌入 690 张卡） | 39.83 s |
| BM25 检索 60 条 | 0.26 s |
| 向量检索 60 条 | 3.27 s |
| ├ 其中：查询嵌入编码 | 2.04 s（占 62%） |
| └ 其中：矩阵乘 + 排序 | 0.006 s |
| 混合融合 60 条（不重排） | 2.15 s |
| **重排 60 条** | **69.1 s** |

重排占 hybrid-rerank 端到端耗时的 **97.0%**。矩阵相似度几乎免费，稀疏检索毫秒级。结论：优化只能从 cross-encoder 下手。

### 13. 两个被测量推翻的假设

**假设一：`max_length=512` 在浪费计算。** 实测候选对只有 27–104 个 token（p50 = 45），512 / 256 / 128 三档测得 93.2 / 100.5 / 92.3 秒，差异落在噪声内。**这个参数不是杠杆**，改它只会让人以为做了优化。

**假设二：逐对处理慢是因为缺少批处理。** 方向对了，但幅度不对。逐对折算约 239 秒，逐组（batch=10）93 秒，跨组 batch=32 为 65 秒——批处理确实有效，但在完整实现里只兑现出 1.16 倍，而不是数量级。

### 14. 困难：跨进程的耗时数字根本不可比

**现象**：同一策略两次评测，`hybrid` 从 3.4 秒变成 60.3 秒，`hybrid-rerank` 从 114.6 秒变成 121.9 秒，而**指标一模一样**（31.7% / 43.3%，MRR 也相同）。

**排查过程**：
1. 先怀疑向量索引缓存失效。检查 `.index/` 目录，两个 `.npz` 都在（7 张卡与 690 张卡各一份）。在**同一进程内**连续构造两次 `VectorRetriever`，两次都是 0.05 秒命中缓存。缓存没有问题。
2. 真实原因是每次进程启动都要**重新加载模型**：嵌入模型约 100 MB、重排模型 1.1 GB。这部分不在向量缓存范围内，而且耗时随操作系统页缓存与 CPU 状态浮动两三倍。

**解决**：所有性能对比改为**在同一进程内**进行——同样的权重、同样的候选、同样的条件，唯一变量是要测的那项改动。

**教训**：**性能数字的测量方法比数字本身更重要**。跨进程比较得出的是"机器当时有多忙"，不是"改动带来了多少收益"。这份记录里早期的耗时数字（3.4 s / 114.6 s）都受此影响，只能用于判断数量级，不能用于精确比较。

### 15. 优化实现与实测收益

- `CrossEncoderReranker.rerank_many(groups)`：把多组候选对拍平、按 `batch_size=32` 分批前向，再按组切回并排序
- `HybridRetriever` 抽出 `_fuse` / `_finalise`，新增 `search_many`
- `KnowledgeBase.search_many` 提供统一入口，不支持批处理的策略自动回退为顺序检索，接口对所有策略都可用

同进程实测（60 组、831 对候选）：

| 实现 | 耗时 |
| --- | --- |
| 逐组重排（原实现） | 105.82 s |
| 一次批处理（新实现） | 91.61 s |
| 提速 | **1.16 x** |
| 排名是否一致 | **完全一致** |

**诚实结论**：这是一次有意义的**无损**优化，但**不是数量级改善**。CPU 上 cross-encoder 的绝对速度（约 130–160 ms/对）才是根本限制。

### 16. GPU 需求评估（结论：目前不需要）

| 场景 | 当前 CPU 耗时 | 是否需要 GPU |
| --- | --- | --- |
| 单次审校请求（约 14 对候选） | 约 1.8 s | 不需要 |
| 60 条查询的批量评测（831 对） | 约 92 s | 不需要 |
| 换用更大的 bge-m3 或多语言重排模型 | 未测 | **需要** |
| 实时高并发审校 | 未测 | **需要** |

真实使用路径是"一条文案审校一次"，约 1.8 秒可以接受。批处理优化解决的是评测效率，不是产品延迟。**只有要验证 bge-m3 的收益时才需要 GPU 资源。**

### 17. 部署时踩的坑

**坑一：AutoDL 镜像缺 `zstd`**，不先补上 Ollama 装不上。

**坑二（最隐蔽）：`pkill -f "ollama serve"` 会杀掉执行它的那个 shell。** shell 自己的命令行里也含 `ollama serve`，`-f` 是全命令行匹配，于是自杀，后续命令根本没有执行。表现是"命令超时且日志没更新"。改用 `pkill -x ollama`（精确匹配进程名）后正常。

**坑三：无卡模式下没有 GPU，上下文会被压到 4096。** Ollama 日志显示 `vram-based default context total_vram="0 B" default_num_ctx=4096`。审校 prompt 要带证据卡片，4096 很可能不够。切到 GPU 后显式设置 `OLLAMA_CONTEXT_LENGTH=8192`，日志确认 `total_vram="23.6 GiB"` 且 `inference compute ... library=CUDA`。**这个坑在准备阶段就发现，比跑完 40 条再发现便宜得多。**

**坑四：非交互式 SSH 会挂住。** `nohup ... &` 不总能让会话立即返回；加上 `disown` 与 `< /dev/null` 后稳定。

### 19. 最有价值的发现：瓶颈不在我预判的地方

我原本以为失败会集中在"模型没删干净夸大表述"。实际轨迹显示未通过的用例是这样失败的：

```
proposal_invalid  attempt 1  type: ValueError
proposal_invalid  attempt 2  type: ValueError
proposal_invalid  attempt 3  type: ValueError
```

**模型输出的 JSON 通不过 Pydantic schema 校验**，而这些用例检索到的证据卡完全正确、弃答判断也对。也就是说 4B 模型的短板是**结构化输出的稳定性**，与"能不能判断事实支撑"是两件事。

这同时验证了项目设计的一个价值：系统没有把不合规的输出当作结果交出去，而是标记为 `needs_revision` 并保留完整轨迹——**护栏在真实模型下确实生效了**，这也说明为什么"结构化弃答"和"返修上限"不是多余的装饰。

**成本**：RTX 3090 约 1.6 元/时。准备（装环境、拉模型，模型还是 4 天前已下载的直接复用）在无卡模式完成，GPU 计费时间约 15 分钟。

## 八、遗留问题

1. **检索绝对水平仍低**（最好 43.3%），不足以支撑生产，目前定位是"可测量的基线"
2. **未在 GPU 上测量**，也未测 bge-m3 或多语言重排模型；中文分组的绝对值预期可提升但**尚无数据**
3. **重排的绝对速度仍是限制**：已做无损批处理优化（1.16 倍），但 CPU 上约 130–160 ms/对的成本由模型规模决定，要跨越需要 GPU
4. **耗时数字不可跨进程比较**（见困难 14）。本文档与结果文档里早期记录的 3.4 s / 114.6 s 只能用于判断数量级
5. **flaky 测试未定位**（见困难 10）
