# 业务问题与方案

## 具体问题

增长团队发布产品落地页、社媒文案时，经常把“支持某功能”写成“所有平台都能用”“一定不卡顿”“自动发布”等更强承诺。多语言文案由不同人改写后，原始产品文档与公开说法容易脱节。人工逐句回查资料可做，但在频繁更新时耗时且难追溯。

本项目的 Agent 执行**发布前的资料核查与修订建议**：读取已有文案，围绕确切产品与功能检索事实卡，定位不实或缺依据的说法，生成保留有依据内容的中英修订稿和来源映射。审核人员最后逐句批准；没有资料时不产出修订稿。

## 输入与输出

- 输入：`product_id`、产品名、语言、功能主题、渠道、已有文案、目标读者；另配一份可替换的产品事实卡和编辑规则。
- 输出：问题清单（引用原文）、修订建议、每条修订主张的来源、原文与修订后的确定性检查、模型工具轨迹、人工审核清单。
- 拒答：检索不到该产品与功能的已核对资料时，状态为 `insufficient_evidence`，没有可审阅修订稿。

## 技术设计

1. 可本地部署的 Qwen3-4B-Instruct 通过 Chat Completions 自主调用 MCP 的 `search_knowledge` 与 `get_editorial_rules`；工具参数和结果由应用验证，按 `product_id` 与 `feature` 隔离。
2. 资料就绪后要求 JSON 结构化输出；应用验证问题引文来自原文、修订引文存在于修订稿、事实 ID 来自本次检索。原文中的禁用短语和无来源数字由程序补充标记，避免模型漏报。
3. 调用 `check_draft` 检查修订稿；只有结构与字面规则通过才标记 `pending_review`。程序不自动发布，也不把引用 ID 的存在等同于语义事实核查。
4. 用带来源的 OBS 官方资料作公开案例。若换产品，替换 JSON 事实库与输入即可，不依赖 OBS 的 API 或内部系统。

## 验证

五条中英开发样例的预期删除片段与弃答标签在 `data/audit_gold.json`。这只检查可复现的字面行为；正式质量评价还需人工逐句判断来源是否支持修订、中文是否自然，并与“不检索的单次 Prompt”和“一次检索 RAG”做同题对照。
